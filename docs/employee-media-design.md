# ระบบรูปภาพและเอกสารพนักงาน (StoredAsset)

เอกสารนี้อธิบายการต่อยอด Cloudinary จากระบบใบสมัครงาน (ดู [job-application-design.md](./job-application-design.md)) ไปใช้กับส่วนอื่นของ TimeTrack — รูปพนักงาน, คลังเอกสารพนักงาน, หลักฐานแนบคำขอ และรูปประกอบประกาศ

---

## 1) ปัญหาที่แก้ตั้งแต่แรก

ตอนกดจ้างงาน โค้ดเดิมเซ็ต `User.photoUrl` เป็น **Cloudinary public_id ดิบ** (เช่น `hr/applications/orphan/clx…`) แต่ทุกหน้าใน UI เอาค่านี้ไปใส่ `<AvatarImage src>` ตรง ๆ เบราว์เซอร์จึงยิงเป็น relative path แล้ว 404 (ไฟล์เป็น `type: authenticated` เปิดตรงไม่ได้อยู่แล้ว) → **รูปพนักงานที่จ้างผ่านระบบใบสมัครไม่เคยแสดงเลย ตกไปที่ตัวอักษรย่อทุกครั้ง**

ทางแก้: `photoUrl` เก็บ **URL ของ route เราเอง** `/api/employees/<id>/photo` ซึ่ง

- คงที่ตลอด — เปลี่ยนรูปกี่ครั้งก็ไม่ต้องไล่แก้ URL ที่ cache ไว้ที่อื่น
- เช็ค session ก่อน แล้ว redirect ไป signed URL
- คืน 404 เมื่อไม่มีรูป และ `photoUrl` จะเป็น `null` เมื่อลบรูปทิ้ง เพื่อให้ fallback ตัวอักษรย่อยังทำงาน

พนักงานที่จ้างไปแล้วก่อนหน้านี้ย้ายด้วยสคริปต์ `prisma/backfill-employee-photos.ts` (รันซ้ำได้)

---

## 2) สคีมา

ตารางเดียว `StoredAsset` ครอบทุกกรณี เพราะไบต์, driver และกติกาการล้างข้อมูลเหมือนกันหมด ต่างกันแค่ `kind` ที่เป็นตัวตัดสินว่าใครดูได้

| ฟิลด์ | ความหมาย |
|---|---|
| `kind` | ประเภท (ดูตารางข้อ 3) — ตัวเดียวที่กำหนดสิทธิ์ |
| `ownerUserId` | พนักงานที่เอกสารนี้**เป็นของเขา** (ไม่ใช่คนอัปโหลด) — null เฉพาะรูปประกาศ |
| `uploadedById` | คนที่กดอัปโหลด |
| `documentExpiresAt` | วันที่เอกสาร**หมดอายุจริงในโลกจริง** (ใบอนุญาตทำงาน/วีซ่า/พาสปอร์ต) — ใช้เตือนเท่านั้น ไม่ใช้ลบ |
| `purgeAfter` | วันที่แถวนี้ควรถูกลบ — ตั้งตอนอัปโหลดเฉพาะไฟล์ที่ยังไม่ผูกกับอะไร |
| `storageDriver` / `storageKey` / `data` | เหมือน `JobApplicationFile` ทุกประการ |

FK ที่ชี้มาหา: `TimeCorrection.attachmentId`, `Advance.attachmentId`, `Announcement.imageAssetId` (ทั้งหมด `onDelete: SetNull`) ส่วน `ownerUserId` เป็น `Cascade`

`src/lib/storage.ts` เดิมผูกกับตาราง `JobApplicationFile` ตายตัวใน driver `db` — เปลี่ยนเป็น `getStorage("storedAsset")` เลือกตารางได้ (Cloudinary ไม่สนใจพารามิเตอร์นี้)

## 3) ประเภทไฟล์และสิทธิ์

นิยามอยู่ที่เดียวใน `src/lib/asset-kinds.ts` (ไฟล์นี้ไม่ import prisma/storage เลย จึงใช้ร่วมกับฝั่ง UI ได้) กติกาทั้งหมดเป็นฟังก์ชัน pure → มีเทสต์ครอบใน `src/lib/__tests__/asset-kinds.test.ts`

| กลุ่ม | kind | อ่อนไหว | มีวันหมดอายุ |
|---|---|---|---|
| รูปพนักงาน | `EMPLOYEE_PHOTO` | – | – |
| คลังเอกสาร | `CITIZEN_ID`, `PASSPORT`, `WORK_PERMIT`, `VISA`, `HOUSE_REGISTRATION`, `BANK_BOOK`, `MEDICAL_CERT` | ✅ | บางประเภท |
| คลังเอกสาร | `EMPLOYMENT_CONTRACT`, `EDUCATION_CERT`, `TRAINING_CERT`, `RESUME`, `OTHER_DOCUMENT` | – | บางประเภท |
| แนบชั่วคราว | `REQUEST_ATTACHMENT`, `ANNOUNCEMENT_IMAGE` | – | – |

**ใครดูได้**

- `EMPLOYEE_PHOTO` / `ANNOUNCEMENT_IMAGE` — ผู้ใช้ที่ล็อกอินแล้วทุกคน (รูปเหล่านี้ขึ้นในทุกหน้ารายชื่อ/ประกาศอยู่แล้ว การกั้นรายคนจะทำให้ทุกลิสต์พัง)
- **เจ้าของดูของตัวเองได้เสมอ** ไม่ต้องมีสิทธิ์ใด ๆ
- คลังเอกสารของคนอื่น — ต้องมี `employee_document.view` และถ้าเป็นเอกสารอ่อนไหวต้องมี `employee_document.view_sensitive` เพิ่ม (**บันทึก audit log ทุกครั้งที่เปิดดู**)
- หลักฐานแนบคำขอของคนอื่น — ต้องมี `request.view`
- `MANAGER` ถูกจำกัดให้เห็นเฉพาะพนักงานสาขาตัวเอง (เหมือนสิทธิ์ใบสมัครงาน) ส่วน ADMIN/HR ไม่ถูกจำกัด

**ใครอัปโหลด/ลบได้**

- รูปตัวเอง — เจ้าของ หรือคนที่มี `employee.edit`
- คลังเอกสาร — เฉพาะ `employee_document.manage` (เจ้าของ **อัปโหลดเองไม่ได้** เพื่อไม่ให้พนักงานเปลี่ยนเอกสารที่ HR เก็บไว้เกี่ยวกับตัวเอง แต่ดูได้)
- หลักฐานแนบคำขอ — เฉพาะเจ้าของคำขอ (ลบได้โดยเจ้าของ หรือคนที่มี `request.approve`)

สิทธิ์ใหม่ seed ด้วย `npx tsx prisma/seed-asset-permissions.ts` (additive — ไม่ลบ RolePermission เดิมที่ปรับผ่าน /admin/permissions ไว้ เหตุผลเดียวกับ seed ของใบสมัครงาน)

## 4) API

| Endpoint | หน้าที่ |
|---|---|
| `POST /api/assets` | อัปโหลดทุกประเภท — ตรวจ mime จาก magic bytes, ปฏิเสธ PDF, จำกัดขนาด (รูป 2MB / เอกสาร 5MB), rate limit 30 ครั้ง/ชม./คน |
| `GET /api/assets/[id]` | เสิร์ฟไฟล์ (`?t=thumb` ได้ 150px) — เช็คสิทธิ์แล้ว redirect ไป signed URL |
| `DELETE /api/assets/[id]` | ลบทั้งไบต์และแถว |
| `GET/DELETE /api/employees/[id]/photo` | รูปพนักงานผ่าน URL คงที่ |
| `GET /api/admin/employees/[id]/documents` | รายการเอกสารของพนักงานคนหนึ่ง |

**Cache** — รูปพนักงาน/รูปประกาศส่ง `private, max-age=300` (ถูกเรียกซ้ำทุกครั้งที่ render ลิสต์) ส่วนเอกสารเป็น `private, no-store` เหมือนไฟล์ใบสมัคร

**การผูกไฟล์แบบสองจังหวะ** — ไฟล์แนบคำขอ/รูปประกาศถูกอัปโหลดก่อนที่ฟอร์มจะถูกส่ง จึงมี `purgeAfter = +24 ชม.` ตั้งแต่แรก และ `claimUploadedAsset()` จะเคลียร์ค่านี้ตอนบันทึกคำขอจริง พร้อมตรวจว่า

1. คนที่อ้างถึงไฟล์คือคนเดียวกับที่อัปโหลด (กันเอาไฟล์คนอื่นมาแนบ)
2. ไฟล์ยังไม่ถูกใช้กับคำขออื่น

ถ้าตรวจไม่ผ่าน **คำขอทั้งใบล้มเหลว** ไม่ใช่บันทึกคำขอที่หลักฐานหายไปเงียบ ๆ

## 5) การล้างข้อมูล

`/api/cron/applications-cleanup` (19:00 UTC ทุกวัน) เพิ่มขั้นตอนกวาด `StoredAsset` ที่ไม่มีใครอ้างถึง — ทั้งกรณี `purgeAfter` เลยกำหนด และกรณีที่ของที่เคยชี้มาถูกลบไปแล้ว (FK เป็น SET NULL ไฟล์จึงค้าง) โดยเช็คจากความสัมพันธ์จริง (`timeCorrections/advances/announcements` ว่างทั้งหมด และเก่ากว่า 24 ชม.)

จุดอื่นที่ลบไบต์ทิ้งด้วย: ลบพนักงานถาวร (`employee-removal.ts` และ `DELETE /api/admin/employees/[id]`), ลบประกาศ, เปลี่ยนรูปพนักงาน (ลบรูปเดิม)

---

## 6) เตือนเอกสารใกล้หมดอายุ

`/api/cron/document-expiry` (01:00 UTC = 08:00 น. ไทย) แจ้งเตือนที่ **60 / 30 / 14 / 7 / 1 / 0 วัน** ก่อนวันหมดอายุ ทั้งกับตัวพนักงานเองและกับทุกคนที่มีสิทธิ์ `employee_document.manage`

ออกแบบให้ **ไม่มี state** — ยิงเฉพาะวันที่ตรงกับตัวเลขข้างต้นพอดี รันทุกวันจึงได้เตือนละครั้งโดยไม่ต้องมีตาราง "เคยส่งแล้ว" ข้อแลกเปลี่ยนคือถ้าวันไหน cron ไม่ทำงานเลย เกณฑ์ของวันนั้นจะถูกข้าม — รับได้เพราะมีหลายเกณฑ์ครอบอยู่

เรื่องนี้สำคัญกับธุรกิจปั๊มโดยเฉพาะ เพราะแรงงานพม่าเป็นกำลังหลักและใบอนุญาตทำงาน/วีซ่าหมดอายุคือความเสี่ยงทางกฎหมายจริง ไม่ใช่แค่งานเอกสาร

## 7) ตอนจ้างงาน

`copyApplicationFilesToEmployee()` **คัดลอก** ไฟล์แนบของผู้สมัครเข้าสู่ระเบียนพนักงาน — รูปถ่ายกลายเป็นรูปพนักงาน ที่เหลือกลายเป็นเอกสารตั้งต้นในคลัง

เดิมออกแบบให้ `User.photoUrl` **ชี้ไปที่ Cloudinary object เดียวกัน**กับไฟล์ของใบสมัครเพื่อประหยัดพื้นที่ แต่พอมีฟีเจอร์ "เปลี่ยนรูปพนักงาน" การผูกร่วมกันแบบนั้นกลายเป็นกับดัก: ลบรูปเก่าทิ้งเมื่อไหร่ ไฟล์ของใบสมัครที่ยังอ้างถึง object เดิมจะพังทันที และกติกาการเก็บข้อมูลของใบสมัครก็จะลามมาถึงแฟ้มพนักงาน จึงเปลี่ยนเป็นคัดลอกจริง — การจ้างงานเกิดไม่บ่อยพอที่ค่าพื้นที่เพิ่มจะคุ้มกว่าความเสี่ยงนี้

ขั้นตอนนี้อยู่**นอก** transaction และไม่ทำให้การจ้างล้มเหลว: การจ้างที่สร้าง `User` ไปแล้วต้องไม่ถูกย้อนกลับเพราะคัดลอกรูปไม่สำเร็จ

## 8) ข้อจำกัดที่ยังอยู่

1. **รับเฉพาะไฟล์รูปภาพ** — บัญชี Cloudinary ปิด "PDF and ZIP files delivery" ไว้ ถ้าอัปโหลด PDF จะเปิดดูไม่ได้เลย จึงปฏิเสธตั้งแต่ต้นทาง ถ้าอยากเก็บสัญญาจ้างเป็น PDF ต้องไปเปิดการตั้งค่านี้ใน Cloudinary console ก่อน
2. **signed URL ไม่หมดอายุจริง** — เหมือนเดิมทุกประการกับระบบใบสมัคร (แพลนปัจจุบันไม่มี token-based authentication) ความปลอดภัยจริงอยู่ที่ route ของเราเป็นคนเดียวที่ออกลิงก์ให้
3. **ไม่มีเซลฟี่ตอนเช็คอิน** — เว้นไว้โดยตั้งใจ ปริมาณรูปต่อเดือนสูงเกินกว่าแพลนปัจจุบันจะรับไหวถ้าไม่มีนโยบายลบอัตโนมัติ และมีประเด็น PDPA เพิ่มอีกชั้น
4. **หนึ่งรูปต่อประกาศ** — ยังไม่รองรับแกลเลอรี
5. **เปลี่ยนรูปแล้วคนอื่นอาจเห็นรูปเก่าได้ถึง 5 นาที** — เพราะ URL รูปพนักงานคงที่และตั้ง `max-age=300` ไว้ ตัวคนที่เปลี่ยนเองเห็นรูปใหม่ทันที (คอมโพเนนต์แสดง preview ในเครื่อง) แลกกับการที่ทุกลิสต์ไม่ต้องยิงขอรูปใหม่ทุกครั้งที่ render
