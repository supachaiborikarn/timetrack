# ระบบที่พักคนงาน + ค่าที่พัก

บริษัทมีบ้านพักให้พนักงาน 3 หลัง ใครอยากอยู่ก็อยู่ได้ ปัญหาคือ **ไม่มีใครรู้ว่าใครอยู่หลังไหน และตรงกับสาขาที่ทำงานหรือเปล่า** — ซึ่งสำคัญเพราะคนที่**ไม่ได้**อยู่บ้านพักบริษัทจะได้เงินค่าที่พักเพิ่ม

---

## 1) สคีมา

### `Dormitory` — บ้านพักแต่ละหลัง

| ฟิลด์ | ใช้ทำอะไร |
|---|---|
| `name` / `code` | ชื่อและรหัสที่พัก (`code` unique) |
| `stationId` | สาขาที่ที่พักนี้รองรับ — **ใช้ตรวจว่าพนักงานอยู่ที่พักตรงกับสาขาที่ทำงานไหม** |
| `capacity` | รองรับได้กี่คน (เว้นว่างได้) — หน้าจอเตือนเมื่อคนเกิน |
| `isActive` | ปิดที่พักโดยไม่ลบข้อมูลว่าใครเคยอยู่ |

### `User` — ข้อมูลที่พักของพนักงาน

| ฟิลด์ | ใช้ทำอะไร |
|---|---|
| `housingStatus` | `UNKNOWN` / `COMPANY_DORM` / `OWN_HOUSING` |
| `dormitoryId` | อยู่หลังไหน (มีค่าเฉพาะเมื่อ `COMPANY_DORM`) |
| `housingAllowance` | ค่าที่พักเฉพาะคนนี้ — **null = ใช้ค่าเริ่มต้นของบริษัท** |
| `housingNote` | หมายเหตุ เช่น "อยู่กับครอบครัว" |
| `housingUpdatedAt` | อัปเดตล่าสุดเมื่อไหร่ — ใช้ดูว่าสำรวจไปถึงไหนแล้ว |

**`UNKNOWN` แยกจาก `OWN_HOUSING` โดยตั้งใจ** — พนักงานทุกคนเริ่มที่ `UNKNOWN` เพราะยังไม่ได้ถาม ถ้าใช้ค่าเดียวกัน "ยังไม่ได้ถาม" จะกลายเป็น "มีสิทธิ์รับเงิน" ทันที และระบบจะจ่ายค่าที่พักให้ทุกคนในบริษัทตั้งแต่วันแรกที่เปิดใช้ กติกานี้อยู่ใน `isEligibleForHousingAllowance()` และมีเทสต์ครอบไว้เฉพาะเคสนี้

## 2) กติกา (`src/lib/housing.ts`)

ไฟล์นี้เป็นฟังก์ชัน pure ทั้งหมด ไม่ import prisma — หน้าจอกับ API จึงตัดสินเรื่องเดียวกันด้วยโค้ดชุดเดียวกัน มีเทสต์ที่ `src/lib/__tests__/housing.test.ts`

**ใครได้เงิน** — เฉพาะ `OWN_HOUSING`

**ได้เท่าไหร่** — `effectiveHousingAllowance()`: ถ้ามีค่าเฉพาะคนใช้ค่านั้น ไม่งั้นใช้ค่าเริ่มต้นของบริษัท (เก็บใน `SystemConfig` key `housing_allowance_monthly`) โดย **0 ที่ตั้งไว้เองถือเป็นค่าจริง** ไม่ใช่ค่าว่าง จึงกดให้คนบางคนไม่ได้เงินได้

**ข้อมูลที่ต้องตรวจ** — `findHousingIssues()` คืนได้หลายข้อพร้อมกัน

| ปัญหา | ความหมาย |
|---|---|
| `MISSING_DORMITORY` | บอกว่าอยู่บ้านพักแต่ไม่ได้เลือกหลัง |
| `DORMITORY_WITHOUT_STATUS` | ยังผูกกับบ้านพักทั้งที่สถานะไม่ใช่ผู้พัก (มักเกิดตอนย้ายออกแล้วแก้ไม่ครบ) |
| `STATION_MISMATCH` | **อยู่บ้านพักคนละสาขากับที่ทำงาน** — ข้อที่ถามหาตั้งแต่แรก |

API บังคับ invariant ให้ด้วย: เปลี่ยนสถานะเป็นอย่างอื่นเมื่อไหร่ `dormitoryId` ถูกล้างทันที และเลือก `COMPANY_DORM` โดยไม่ระบุหลังจะถูกปฏิเสธ

## 3) หน้าจอ — `/admin/housing`

3 แท็บ

1. **ผังพนักงาน** — พนักงานทุกคนพร้อมสาขา สถานะที่พัก และปัญหาที่เจอ กรองตามสาขา/สถานะ/เฉพาะที่ต้องตรวจ และค้นหาชื่อได้ เรียง `UNKNOWN` ขึ้นก่อนเพราะเป็นงานที่ยังต้องทำ
2. **ที่พัก** — เพิ่ม/แก้ไขบ้านพัก 3 หลัง ผูกกับสาขา ตั้งจำนวนที่รองรับ และดูว่าตอนนี้มีกี่คน (เตือนถ้าเกิน)
3. **ค่าที่พัก** — ตั้งค่าเริ่มต้นของบริษัท และสร้างรายการประจำเดือน

การ์ดสรุปด้านบนตอบคำถามตั้งต้น: ทั้งหมดกี่คน / ยังไม่ระบุกี่คน / อยู่บ้านพักกี่คน / อยู่เองกี่คน / ข้อมูลต้องตรวจกี่คน

**การลบที่พัก** ทำได้เฉพาะตอนไม่มีใครผูกอยู่ — FK เป็น `SET NULL` ถ้าลบทั้งที่มีคนอยู่ ข้อมูลว่าใครอยู่หลังไหนจะหายเงียบ ๆ ระบบจึงให้ "ปิดใช้งาน" แทน

## 4) เงินค่าที่พักไหลเข้าเงินเดือนยังไง

กด "สร้างรายการค่าที่พักประจำเดือน" → ระบบสร้าง `SpecialIncome` type `HOUSING_ALLOWANCE` ให้คนที่มีสิทธิ์ทีละคน แล้ว**เงินเดือนดึงไปคิดเอง** เพราะ `payroll-service` รวม `SpecialIncome` ทุกรายการในช่วงวันที่อยู่แล้ว — ไม่ได้สร้างทางคำนวณเงินเดือนเส้นที่สองขึ้นมาใหม่

- **สถานะ `PENDING`** เหมือนโบนัส/ทิปที่สร้างจากหน้ารายได้พิเศษ และแก้/ลบได้จากหน้านั้นตามปกติ
- **ลงวันที่วันสุดท้ายของเดือน** — เป็นวันเดียวที่ตกอยู่ในงวดที่ถูกต้องไม่ว่างวดจะเป็นเดือนปฏิทินหรือรอบ 26–25 ที่หน้าเงินเดือนมีให้เลือก
- **กดซ้ำได้** — ข้ามคนที่มีรายการ `HOUSING_ALLOWANCE` ในเดือนนั้นแล้ว เพิ่มพนักงานใหม่กลางเดือนแล้วกดอีกรอบจึงเป็นการเติมให้เฉพาะคนที่ขาด ไม่ใช่จ่ายซ้ำทั้งกอง
- **คนที่ค่าที่พักเป็น 0 จะถูกข้าม** และหน้าจอเตือนไว้ก่อนกด — กันการสร้างรายการ 0 บาทเป็นพรืดตอนที่ยังไม่ได้ตั้งอัตรา
- เช็ค "จ่ายไปแล้วหรือยัง" ด้วย query เดียวสำหรับทั้งเดือน ไม่ใช่ยิงรายคน

หน้า preview กับตอนกดสร้างใช้ฟังก์ชัน `collect()` ตัวเดียวกัน — สิ่งที่ HR เห็นก่อนกดคือสิ่งที่จะถูกเขียนจริง

## 6) ข้อจำกัดที่ยังอยู่

1. **ไม่มีประวัติการย้ายที่พัก** — เก็บแค่สถานะปัจจุบันกับ `housingUpdatedAt` ถ้าต้องการย้อนดูว่าเดือนไหนใครอยู่ที่ไหน ต้องเพิ่มตารางประวัติ (ตอนนี้ดูจาก audit log ได้อย่างเดียว)
2. **เหมาจ่ายรายเดือนเต็มจำนวน** — คนที่เข้างานกลางเดือนหรือลาออกกลางเดือนก็ได้เต็ม ต้องแก้จำนวนเงินเองในหน้ารายได้พิเศษ
3. **ยังไม่ผูกกับการลาออก** — พนักงานที่ปิดใช้งานแล้วจะไม่ถูกนับ (query กรอง `isActive`) แต่ `dormitoryId` ยังค้างอยู่ ต้องย้ายออกเอง
4. **ไม่มีที่ให้พนักงานแจ้งเอง** — เป็นข้อมูลที่ HR สำรวจแล้วกรอกให้ ไม่ได้เปิดให้พนักงานแก้สถานะที่พักของตัวเอง (เพราะมีผลต่อเงิน)
